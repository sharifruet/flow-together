# TogetherFlow — UI Requirements Document

Status: Draft v1
Owner: TBD
Current state: see [STATUS.md](STATUS.md) — what is built, what is verified, and what is not.
Scope: net-new React front end(s), branded **TogetherFlow**, for this repository's engines (BPMN, CMMN, DMN, App, IDM, Event Registry)

## 1. Purpose

This repository (`flow-together`, a fork of `flowable-engine`) currently ships **engines and REST APIs only** — there is no bundled UI. Historically, upstream Flowable shipped four AngularJS single-page apps (Task, Modeler, Admin, IDM) that consumed those same REST APIs; those apps are long deprecated and are not present here. Flowable's commercial Enterprise product has since replaced them with a **React-based front end** ("Flowable Design", "Flowable Work", "Flowable Control"), confirming React as a sound, vendor-validated direction.

This document defines requirements for building an equivalent set of React UIs against **this project's own REST modules**, using the Enterprise product's application boundaries and feature set as the requirements source, not as something we integrate with or reuse code from — and its own product identity: **TogetherFlow**.

**Naming convention used throughout this document**: "TogetherFlow" is the product/brand name — what appears in the UI itself (browser tab titles, login screen, app switcher, logo/wordmark) and in the module/package names for everything built here (§10). "Flowable" continues to refer, factually, to the underlying engine this repo forks and to the real Flowable/Flowable Enterprise product used as requirements source material (§2, §5's "Enterprise equivalent" column, §9) — that usage is never renamed, since it names something that actually exists outside this effort. The four sub-apps are **TogetherFlow Work**, **TogetherFlow Control**, **TogetherFlow Identity**, and **TogetherFlow Design**, composed under **TogetherFlow Shell** (§7.5); body text may shorten these to "Work," "Control," etc. after each section's first mention, the same way this document already does.

## 2. Sources

- Flowable Enterprise Documentation, https://documentation.flowable.com/latest/ — architecture overview (`admin/installs/platform-full`), Work user guide (`user/work/`), Control/admin reference (`user/control/`), Hub access control (`user/hub/hub-configuration/access-control`), React Design migration guide (`develop/migration/new-design-migration-guide`).
- Flowable open-source docs, https://www.flowable.com/open-source/docs/bpmn/ch13-Applications — describes the legacy Task/Modeler/Admin/IDM app boundaries this OSS engine was built around.
- This repository's own REST layer: `modules/flowable-rest`, `flowable-cmmn-rest`, `flowable-dmn-rest`, `flowable-idm-rest`, `flowable-app-engine-rest`, `flowable-event-registry-rest`, `flowable-external-job-rest` (resource classes enumerated in §5/§7), and the published specs under `docs/public-api/references/{openapi,swagger}/{process,cmmn,decision,app,eventregistry}`.

**Key finding**: the Enterprise product organizes UI around four concerns — model authoring, task/case work, operations, and identity. It also includes cloud-only concepts (Hub multi-cluster admin, Engage customer messaging, Inspect debugging) that don't map to anything this OSS engine exposes — see §9 (Out of Scope).

## 3. Goals

- Ship a modern, TypeScript React UI per concern, each independently deployable, all consuming this repo's existing REST APIs unmodified.
- Cover the day-to-day workflows the legacy Task/Admin/IDM apps covered: work on tasks and cases, start process/case instances, monitor and manage runtime and history, manage users/groups/privileges.
- Reuse the OpenAPI/Swagger specs already generated by this repo (`docs/public-api`) as the source of truth for a typed API client, instead of hand-rolling fetch calls.
- Fit the existing Maven multi-module reactor convention (`modules/togetherflow-*`) so the UI builds alongside the engines via `./mvnw`, per [CLAUDE.md](../../CLAUDE.md).

## 4. Non-Goals

- Multi-cluster/environment administration ("Hub"), customer messaging ("Engage"), release-debugging tooling ("Inspect") — enterprise-cloud concepts with no backing REST surface in this repo. Not planned at any phase — see §9.
- Mobile native apps.
- Authentication provider itself (SSO/OIDC broker) — TogetherFlow authenticates *against* an identity provider (OIDC Authorization Code + PKCE, see ADR 0006) but does not implement one.
- Porting the Enterprise Design app's closed-source palette/config format (`flowable.design` JSON palettes, `presentationId` icon refs) — if we build a visual modeler (in scope, §7.4), its configuration system is a fresh design, not a port.

Everything else — including the visual BPMN/CMMN/DMN/Form/App/Event-Registry model editors — **is in scope**; §7.4 covers it in full and §12 sequences it into later phases so Work/Control/Identity ship first. "Later phase" is a build-order decision, not a requirements gap.

## 5. Application Inventory

Each proposed app maps to a legacy Flowable app, an Enterprise equivalent, and the REST module(s) in this repo it will actually call.

| # | TogetherFlow app | Legacy OSS equivalent | Enterprise equivalent | Backing REST module(s) here |
|---|---|---|---|---|
| 1 | **TogetherFlow Work** (task + case inbox) | Task app | Flowable Work | `flowable-rest` (Task*, ProcessInstance*), `flowable-cmmn-rest` (Task*, CaseInstance*, PlanItemInstance*) |
| 2 | **TogetherFlow Control** (ops/admin console) | Admin app | Flowable Control | `flowable-rest`, `flowable-cmmn-rest`, `flowable-dmn-rest`, `flowable-event-registry-rest`, `flowable-external-job-rest` (Job*, Batch*, Deployment*, HistoricXxx*, Table*, ChannelDefinition*, EventDefinition*, EventInstance* — send only, see §7.2 — ExternalWorkerJob*) |
| 3 | **TogetherFlow Identity** (users/groups/privileges) | IDM app | IDM within Hub | `flowable-idm-rest` (User*, Group*, Privilege*) |
| 4 | **TogetherFlow Design** (BPMN/CMMN/DMN/Form/Event/App **modeling and deployment**) | Modeler app | Flowable Design | `flowable-app-engine-rest` (AppDefinition*, AppDeployment*, AppModel*), plus each engine's Deployment*/Model* resources: `flowable-rest` (Model*, ProcessDefinition*), `flowable-cmmn-rest` (CaseDefinition*), `flowable-dmn-rest` (Decision*, DecisionTable*), `flowable-event-registry-rest` (ChannelDefinition*, EventDefinition*) |

A fifth piece, **TogetherFlow Shell**, is not a business app but the composition layer: login, cross-app navigation, and shared auth/session state — analogous to how the legacy apps shared one IDM-backed SSO cookie. The "Flowable" name never appears in the product's own UI chrome — see the branding requirement in §7.5.

Note: `flowable-rest`'s `Model*` resources (`ModelCollectionResource`, `ModelResource`, `ModelSourceResource`, `ModelSourceExtraResource`) are the closest thing this repo has to a standalone pre-deployment model repository — draft process models saved as JSON/XML with source + thumbnail, independent of any deployment. This is what backed the legacy Modeler app's "save draft, deploy later" workflow, and Design (§7.4) is built on it rather than only working with already-deployed artifacts. There is no equivalent standalone repository for case (CMMN), decision (DMN), or form models in this repo's REST layer today — see the gap called out in §7.4.6 and §11.

## 6. Personas

- **Business user** — works the Work app inbox: claims/completes tasks, fills in forms, tracks cases they're involved in.
- **Process/case owner** — starts new process/case instances, monitors instances they started, acts on exceptions.
- **Operations/administrator** — uses Control to inspect runtime state, retry failed jobs, manage deployments, query history and raw tables.
- **Identity administrator** — uses Identity to provision users/groups and grant privileges (e.g., who may access Control or Design).
- **Citizen developer / analyst** — authors and deploys process, case, decision, form, event/channel and app models via Design (built later than Work/Control/Identity — see §12 — but a fully-scoped persona, not an afterthought).

## 7. Functional Requirements

Endpoint names below are the actual resource classes found in this repo (§5), not invented.

### 7.1 TogetherFlow Work

- **Task inbox**: list tasks assigned to me / my groups / unassigned-claimable, backed by `TaskQueryResource` (BPMN) and `TaskQueryResource` (CMMN). Filter by process definition, due date (overdue / today / this week / none), priority band, and involved user (`TaskIdentityLinkCollectionResource`); filter sets can be saved and reapplied (§14.4). Case-definition filtering is not offered: the shared task table exposes `processDefinitionKey` but no equivalent scope filter through this repo's query resource.
- **Task detail**: view/edit task variables (`TaskVariableCollectionResource`, `TaskVariableDataResource`), comments (`TaskCommentCollectionResource`), attachments (`TaskAttachmentCollectionResource` — storage backend is pluggable, see §7.6), identity links (involved people/groups), sub-tasks (`TaskSubTaskCollectionResource`), audit log (`HistoricTaskLogCollectionResource`).
- **Task actions**: claim, unclaim, assign, delegate, complete, complete-with-form-data — all via `TaskResource`/`TaskBaseResource`.
- **Case work**: case instance list/detail via `CaseInstanceQueryResource`/`CaseInstanceResource`, active plan items via `PlanItemInstanceCollectionResource`, milestones via history equivalents.
- **Start new work**: browse startable process definitions/case definitions (`ProcessDefinitionCollectionResource`, `CaseDefinitionCollectionResource`) filtered by what the current user is authorized to start, start with initial variables.
- **My history**: completed tasks and instances I was involved in, via `HistoricTaskInstanceQueryResource` / `HistoricProcessInstanceQueryResource` / `HistoricCaseInstanceQueryResource`.
- **Forms**: task forms render natively from the engine's own form model, fetched via `GET /runtime/tasks/{taskId}/form` (and `/repository/process-definitions/{id}/start-form` for start forms). The typed variable grid remains as a fallback for tasks with no form, or when the form model cannot be loaded. See [ADR 0007](adr/0007-flowable-native-form-renderer.md). `upload` fields are supported on a task, where the attachment endpoint gives the file somewhere to go; a start form has no such endpoint and says so rather than showing a control that cannot work. Expression-driven option lists arrive unresolved from the engine and fall back to a free-text input.

### 7.2 TogetherFlow Control

- **Process instances**: query/list/filter (`ProcessInstanceQueryResource`), detail with diagram overlay of current activity (`ProcessInstanceDiagramResource`, `ActivityInstanceCollectionResource`), variables, identity links; delete/suspend/activate/migrate.
- **Case instances**: equivalent, via `CaseInstanceQueryResource`, `CaseInstanceDiagramResource`, `PlanItemInstanceQueryResource`.
- **Decision executions**: history of DMN evaluations via `HistoryDecisionExecutionCollectionResource`, with input/output payload inspection.
- **Deployments**: list/inspect/delete BPMN, CMMN, DMN and App deployments and their resources (`DeploymentCollectionResource` × engine, `DeploymentResourceDataResource` for downloading raw XML/diagrams).
- **Definitions**: suspend/activate process definitions (`ProcessDefinitionResource` supports this; **CMMN case definitions and DMN decisions do not** — this repo's REST layer only exposes suspend/activate at the process-definition level, so Control's UI must not offer that action for case/decision definitions). Manage authorized starters (which users/groups may start a given process or case) via `ProcessDefinitionIdentityLinkCollectionResource` / `CaseDefinitionIdentityLinkCollectionResource`.
- **Jobs**: async, timer, dead-letter, suspended and history job queues per engine (`JobCollectionResource`, `TimerJobCollectionResource`, `DeadLetterJobCollectionResource`, `SuspendedJobCollectionResource`, `HistoryJobCollectionResource` — the latter covers async history handling, including history cleanup jobs), with retry/move/delete actions and exception stack trace viewer (`JobExceptionStacktraceResource`).
- **Signals & messages**: broadcast a signal or trigger a message event from the admin console (`SignalResource`) — useful for unblocking stuck instances waiting on an event that never arrived externally.
- **Batches**: batch and batch-part inspection (`BatchCollectionResource`, `BatchPartCollectionResource`) for bulk operations like process migration.
- **Event subscriptions**: list/inspect signal & message subscriptions (`EventSubscriptionCollectionResource`).
- **Event Registry runtime**: deployed channel/event definitions and their JSON/XML source (`ChannelDefinitionCollectionResource`, `EventDefinitionCollectionResource`, `*ModelResource`, `*ResourceDataResource`), plus a send-an-event tool for confirming that a deployed event starts what it should (`EventInstanceCollectionResource`).
- **Inbound event log** — *served by an optional module, not by the engine.* This section previously cited `EventInstanceCollectionResource` as the source of "events received on a channel". It is not one: that resource is **POST-only** — it *sends* an event into the registry — and the event registry engine persists repository state only (deployments, resources, event and channel definitions). Nothing records what arrived, by design, since an inbound channel can carry high-throughput traffic and the engine routes events to their subscriptions rather than logging them. A received-events feed therefore needed **new backend surface**, and got it: `togetherflow-event-recorder` (§10) records inbound events from inside the application hosting the engine and exposes its own `GET`. Control shows a **Received** tab wherever that module is deployed, listing what arrived, on which channel, and whether it dispatched, matched nothing, or was rejected — and shows no such tab at all where it is not, since an absent feed and an empty one mean different things. The recorder is off by default and adds a write to the inbound path when on. See [ADR 0015](adr/0015-inbound-event-log.md).
- **External worker jobs**: queue of jobs acquired by/available to external workers, with unlock/unacquire actions (`ExternalWorkerJobCollectionResource`, `ExternalWorkerJobResource`, `ExternalWorkerUnacquireJobResource`) — distinct from the async/timer job queues above since external workers poll rather than get pushed to.
- **Database explorer**: raw table list, row browsing, and column metadata (`TableCollectionResource`, `TableDataResource`, `TableColumnsResource`) — read-only, admin-privileged.
- **Engine properties**: engine version/health info (`EnginePropertiesResource`, per-engine `*EngineResource`, including `EventRegistryEngineResource`).

### 7.3 TogetherFlow Identity

- **Users**: CRUD (`UserCollectionResource`/`UserResource`), profile picture (`UserPictureResource`), custom user info key/value pairs (`UserInfoCollectionResource`/`UserInfoResource`).
- **Groups**: CRUD and membership management (`GroupCollectionResource`, `GroupMembershipCollectionResource`).
- **Privileges**: assign/revoke privileges to users and groups, used elsewhere to gate access to Control/Design (`PrivilegeCollectionResource`/`PrivilegeResource`).
- **Engine health**: `IdmEngineResource`.
- **LDAP awareness**: when the deployment is configured with `flowable-ldap` (a module already in this repo) instead of the default database-backed IDM, users/groups are sourced read-only from the directory. The UI must detect this (e.g. a flag surfaced via `IdmEngineResource`, or a config value passed from the shell) and disable create/edit/delete affordances for LDAP-sourced identities instead of letting them fail against a read-only backend.

### 7.4 TogetherFlow Design (modeling)

Design is the authoring surface for every model type this repo's engines can execute. Each sub-section below is a full requirement, independent of when it's built (§12 sequences the build order — process/case modeling ships before form/event/app modeling).

**Confirmed**: BPMN, CMMN, DMN, Forms and Event Registry modeling are all required — none of these are optional or under debate. Where a sub-section calls out an "open question" (CMMN in §7.4.3, Forms/Event Registry in §7.4.6), that question is about *implementation approach* (canvas strategy, draft-repository design) and build sequencing (§12), not about whether the feature ships.

#### 7.4.1 Model library (shared across all model types)

- Single library view listing all draft models (`ModelCollectionResource`) plus, where a type has no draft repository (CMMN/DMN/Form/Event — see §7.4.6), the models found inside existing deployments.
- Filter/search by type (process, case, decision, form, channel, event, app), name, key, creator, last-modified.
- Thumbnail preview, version history, "duplicate", "rename", "delete" (draft only — deployed models are immutable, superseded by a new version instead). **Version history is built** on the engine's own model versioning (`version` / `latestVersion` on `ModelCollectionResource`) rather than a side table: a version is cut on deploy and on demand, the highest version is the working draft, and restoring an older one cuts a version from the current contents first so nothing is lost. Diffing two versions is deliberately absent — a real BPMN diff is a graph comparison, and a text diff of serialised XML would mostly report attribute reordering.
- Import existing BPMN/CMMN/DMN XML or form/event JSON as a new draft; export any model back to its native file format.

#### 7.4.2 BPMN process modeler

- Canvas + palette editor for BPMN 2.0: events (start/end/intermediate, all trigger types), gateways (exclusive/parallel/inclusive/event-based), tasks (user/service/script/manual/receive/business-rule/call-activity), sub-processes (embedded/event/transaction), sequence/message flows, pools & lanes, data objects.
- Properties panel per element: id/name/documentation, assignee/candidate users & groups on user tasks, form key binding, execution/service listeners, extension elements the engine already supports (e.g. `flowable:` namespace attributes used by `flowable-bpmn-converter`).
- XML source view (round-trips through `flowable-bpmn-converter`, which this repo already ships), validation against `flowable-process-validation` before save/deploy. **Built, server-side**: `POST /repository/model-validation` (`ModelValidationResource` in `flowable-rest`) runs the engine's own `ProcessValidator` over submitted XML and returns every problem it reports, deploying nothing and storing nothing — so what the modeller shows and what a deploy would reject are the same list. This is new REST surface added by this fork rather than an upstream resource; it is one resource class over an existing engine capability, with no schema change. Design's in-browser checks remain, labelled as such, for feedback while typing and for when the engine is unreachable.
- Save as draft (`ModelResource`/`ModelSourceResource`), deploy (`DeploymentCollectionResource` in `flowable-rest`), or bundle into an app (§7.4.5).
- Built on `bpmn-js` (Modeler mode) — mature, actively maintained, BPMN-2.0-standard-compliant OSS canvas; Flowable extension attributes are added via a custom `bpmn-js` moddle extension, not a fork.

#### 7.4.3 CMMN case modeler

- Canvas + palette for CMMN 1.1: stages, human/process/case/decision tasks, milestones, event listeners, sentries (entry/exit criteria), case file model (case variables), plan fragments.
- Same round-trip/validation/save/deploy pattern as BPMN, via `flowable-cmmn-converter` and `flowable-case-validation`, deploying through `flowable-cmmn-rest`'s `DeploymentCollectionResource`. Validation is the counterpart resource `POST /cmmn-repository/model-validation`, running the engine's own `CaseValidator`, merged with in-browser checks in the same way BPMN merges its own, with a badge on each problem saying which side reported it. The browser checks are deliberately **disjoint** from the engine's: `CaseValidator` reports four problems in total (decision task with no reference, human-task listener with no implementation or no event, empty plan model), so the browser side covers what it does not look at — duplicate ids, a process or case task naming nothing to start, a timer with no expression, a service task with no implementation, an HTTP task missing `requestUrl`/`requestMethod`, an empty stage, a criterion that waits for nothing. Those run on every edit, debounced, and mark the shapes on the canvas as well as listing the problems; the engine's verdict costs a round trip so it arrives on an explicit check or a deploy, and the panel's caveat says which of the two the reader is looking at.
- **Palette and properties now cover what the engine reads** (see STATUS.md §2f): all 21 plan item kinds — including the six typed tasks (script, HTTP, mail, external worker, case page, send event), the four typed event listeners (signal, variable, intent, reactivate) and the plan fragment — plus roughly 40 `flowable:` attributes the panel previously could not set, `<documentation>`, `<defaultControl>` and `<planItemStartTrigger>`. Attribute names are checked against `CmmnXmlConstants.java` by a test, because a misspelt one is written, round-trips, deploys, and silently does nothing.
- **Two things are deliberately absent, not backlog.** `<textAnnotation>` and `<association>` are declared in the CMMN 1.1 schema but appear in no content model, and `CmmnDeployer` schema-validates every new deployment — an annotated case cannot be deployed. The `<caseFileModel>` is schema-valid but `caseFileItem` appears nowhere in Flowable outside the XSD: no converter, no model class, no engine support, so an editor for it would produce configuration that does nothing. Both are preserved on round trip and left alone.
- **Known gap**: unlike BPMN and DMN, there is no actively maintained OSS canvas library equivalent to `bpmn-js` for CMMN — `bpmn.io`'s CMMN effort was never completed. This sub-app needs either (a) a custom canvas built in-house (larger effort, own design pass required against `flowable-cmmn-model`'s object model) or (b) a scoped-down first cut (e.g. a stage/task list-and-properties editor without a free-form canvas) shipped first with the full graphical editor as a follow-up. Flag this explicitly to whoever prioritizes Phase 5 (§12) — it is the single largest unknown in this whole document.

#### 7.4.4 DMN decision modeler

- **Decision table editor**: hit policy selector, input/output column definitions (including FEEL expressions), rule grid with add/remove/reorder rows, input-clause value lists.
- **DRD (Decision Requirements Diagram) editor**: for decision services composed of multiple linked decision tables, via `dmn-js`'s DRD mode.
- Round-trips through `flowable-dmn-xml-converter`; validate, save draft, deploy via `flowable-dmn-rest`'s `DmnDeploymentCollectionResource`.
- Built on `dmn-js` (also `bpmn.io`) — supports both the table editor and DRD out of the box; well matched to this repo's DMN engine since both target the OMG DMN standard.

#### 7.4.5 App definition builder

- Compose a deployable "app" by selecting existing process/case/decision/form/event models (from the library, §7.4.1) plus metadata (name, key, icon, theme color), matching `AppDefinitionResource`'s model.
- Publish/deploy the composed app as a single unit (`AppDeploymentCollectionResource`), and re-open a previously published app definition for editing (creates a new version, per this engine's deployment-versioning convention — nothing here is mutated in place).
- List and manage existing app deployments and their bundled resources (`AppDeploymentResourceCollectionResource`, `AppDeploymentResourceDataResource`).

#### 7.4.6 Form builder and Event Registry channel/event modeler

- **Form builder**: drag-and-drop field palette (text, number, date, dropdown, radio/checkbox, upload, HTML/display text), field validation rules, outcome/submit buttons, binding fields to process/case variables. Renders using the same component at runtime in Work (§7.1) so authoring and execution stay visually consistent.
- **Event/channel modeler**: define inbound/outbound channel definitions (JMS/Kafka/RabbitMQ/HTTP, per whatever channel adapters this repo's `flowable-event-registry` ships) and event definitions (payload correlation keys, mapping to process/case start or signal events).
- **Gap to resolve before building either**: neither has a standalone draft-model REST repository the way BPMN does. `flowable-form-model`/`flowable-form-api` define the JSON schema but there's no `flowable-form-rest`; Event Registry's REST module only exposes deployment-derived models (`ChannelDefinitionModelResource`, `EventDefinitionModelResource`), not a pre-deployment draft CRUD API. Two options, to be decided before Phase 5/6 (§12) starts: (a) add a small new REST module (`flowable-form-rest`, and draft-CRUD endpoints on `flowable-event-registry-rest`) mirroring `ModelResource`'s shape, or (b) author these client-side and package them directly as deployment resource bytes inside a process/case/app zip upload, skipping a draft-save step entirely. This is a backend-touching decision, not purely a frontend one — call it out to whoever scopes the corresponding engine work.
- Also note: `@bpmn-io/form-js` exists as an OSS form builder/renderer, but its JSON schema is Camunda's own, not `flowable-form-model`'s — it cannot be dropped in as-is; either write a schema adapter or build a Flowable-schema-native builder from scratch. Decide alongside the gap above.

### 7.5 TogetherFlow Shell (cross-cutting)

- **Branding**: every user-visible surface — browser tab title, favicon, login screen, logo/wordmark, app switcher labels, footer/about text — shows **TogetherFlow**, not "Flowable." "Flowable" is this product's underlying engine, referenced only where technically necessary (e.g. an admin-facing engine-version string in TogetherFlow Control's engine properties view, §7.2), never as the product's own identity. Apply this in `togetherflow-common`'s theme/branding tokens once, so no individual app can drift from it.
- **Logo asset**: the canonical logo lockup lives at [`logo.png`](./logo.png) (checked in beside this document) — a cloud-shaped icon built from a start→task→gateway→task→end workflow glyph over three person silhouettes, paired with the "TogetherFlow" wordmark ("Together" in navy, "Flow" in teal). It's the source of truth for the color palette in §14.2 and the icon shape TogetherFlow Shell's favicon and app-switcher mark derive from. It's a flat PNG, which is a starting point, not the final asset: before Phase 1 ships anything, get a proper vector source (SVG/AI) from whoever owns the brand, plus the standalone icon mark (no wordmark) cropped tight for favicon/small-size use — a wordmark that small is illegible, and a raster-only logo won't scale cleanly across the very different surface sizes this needs (16px favicon through a full login-screen hero).
- Login screen against `flowable-idm-rest`; session/token storage; logout.
- App switcher (TogetherFlow Work / Control / Identity / Design), gated by privilege checks from §7.3.
- Tenant context: surfaces the active tenant (switcher, if a user can access more than one) and makes it available to every app for list filtering and deploy/start actions — see the Multi-tenancy NFR in §8.
- Global error/toast handling for API failures, consistent loading/empty states.
- User menu: profile, change password (if supported by IDM), theme toggle (light/dark).

### 7.6 Attachment storage (pluggable, cross-cutting)

Grounded in the actual engine model: `Attachment` (`flowable-engine`'s `org.flowable.engine.task.Attachment`) has **either** a `url` (external link, no bytes ever pass through Flowable) **or** a `contentId` (bytes stored as a `ByteArrayEntity` row in this engine's own database). `TaskService.createAttachment` has a matching overload for each, and — confirmed by reading it — `flowable-rest`'s `TaskAttachmentCollectionResource` already exposes *both* at the same endpoint: multipart upload for the byte-storage path, and a JSON body with `externalUrl` for the link path. This is the natural seam for "local vs. SharePoint" — it doesn't need new engine changes, only a UI-layer decision of which path to call.

- **`db` provider (default, per this requirement)**: Work app's attachment widget posts multipart directly to `TaskAttachmentCollectionResource`. Zero new infrastructure — this is what the engine already does today, out of the box, with content living in this deployment's own database. A fresh install works with no attachment-storage configuration at all.
- **`sharepoint` provider**: uploads can't go straight from browser JS to Microsoft Graph (app credentials would be exposed client-side), so this mode requires a small backend proxy — see the new `togetherflow-attachment-gateway` module in §10 — that: (1) receives the file from the Work app, (2) uploads it to a configured SharePoint document library via Microsoft Graph API using app-only auth (Azure AD app registration, client-credentials grant, `Sites.Selected` or `Sites.ReadWrite.All` permission scoped to the target site), (3) calls Flowable's existing `TaskAttachmentCollectionResource` with `externalUrl` set to the returned SharePoint item's `webUrl`. Reads need no proxy — the UI just opens the stored URL; SharePoint handles the viewer's own Microsoft 365 auth.
- **`filesystem` provider** (optional third mode, if a true local-disk tree is wanted instead of/alongside the DB): same gateway as SharePoint, but writes to a configured local directory and stores back a URL pointing at the gateway's own download endpoint, instead of calling Graph.
- **Configuration**: a single switch selects the active provider — `togetherflow.attachments.provider=db|sharepoint|filesystem`, **defaulting to `db`** — with provider-specific config nested under it (SharePoint tenant/client/site/drive/folder; filesystem base path). One property change is the entire migration path between providers — no code change, no data migration for existing attachments (old ones keep resolving via whichever path created them, since `url` and `contentId` coexist per-row). This is what makes it "configurable easily": switching providers is ops config, not a rebuild.
- Applies wherever attachments show up — Work app (§7.1) is the primary surface; Control (§7.2) inherits it for free when displaying task/case history that includes attachments.
- The `togetherflow-attachment-gateway` module is only deployed at all when a non-`db` provider is configured — with the default, this whole piece of infrastructure simply doesn't exist for a given install.

## 8. Non-Functional Requirements

- **Typed API client**: generate TypeScript clients from the existing OpenAPI specs in `docs/public-api/references/openapi/{process,cmmn,decision}` and the Swagger specs for `app`; `flowable-idm-rest` is not covered by the engine's own spec generation, so a spec was hand-authored at `docs/public-api/references/openapi/idm/flowable-oas-idm.yaml` and wired into the same codegen and contract-drift check as every other engine. It is derived by reading the resource classes and must be kept in step with them — the conformance assertions in `contract.test-d.ts` fail the build if the client and the spec disagree.
- **Auth**: OIDC Authorization Code + PKCE against a public client, tokens held in memory with silent renewal (ADR 0006). HTTP Basic remains available for local development only and refuses to run over plain HTTP outside loopback. The API client consumes an injected header callback, so the mechanism is swappable without touching feature code.
- **i18n**: all user-facing strings externalized (legacy apps supported translation packs; don't regress). Built as an in-house layer in `togetherflow-common` — see [ADR 0013](adr/0013-in-house-i18n.md) — with one catalogue per module, merged at the root. Every module's strings are externalized and dates follow the active locale. **Only `en` ships**: the machinery is complete and adding a language is additive, but nothing is translated yet. This was *not* done from day one, contrary to what this bullet asked for; it was retrofitted after Phase 6, at the cost the plan predicted.
- **Accessibility**: WCAG 2.1 AA as a baseline for the Work app in particular, since it's used by non-technical business users all day.
- **Responsiveness**: Work app must be usable on tablet width (task triage on the go); Control/Identity/Design are desktop-first (data-dense tables/diagrams).
- **Performance**: task/instance lists must page/virtualize server-side (all list resources already support `start`/`size`/sort query params) — never load unbounded result sets client-side.
- **Browser support**: last 2 versions of evergreen browsers (Chrome, Edge, Firefox, Safari); no IE11 (legacy AngularJS apps had to support it, this doesn't).
- **Multi-tenancy**: this repo's query/collection resources across every engine accept a `tenantId` filter (confirmed on e.g. `ProcessDefinitionCollectionResource`, `ProcessInstanceQueryResource`, and the equivalent CMMN/DMN/App resources). This is cross-cutting, not one app's concern: Shell needs a tenant context (switcher or fixed-per-login-tenant, TBD — see §11), Work/Control must filter every list by the active tenant, and Design must let a deploy/publish action target a specific tenant. Treat "which tenant is this list/action scoped to" as a first-class piece of app state from Phase 1 onward, not something bolted on later — retrofitting it after list/query components are built without a tenant parameter is expensive.
- **Testing**: unit/component tests (Vitest + React Testing Library) per module, plus end-to-end coverage (Playwright) for the golden paths in §7 (complete a task, start a process, deploy a model, retry a job, create a user) run against a real instance of this repo's REST layer — not mocked responses — so contract drift between frontend and backend is caught. Wire into the existing `./mvnw verify` flow per module's `pom.xml`, consistent with how the rest of this reactor runs its test suite.

## 9. Out of Scope / Explicitly Not Building

Concepts found in the Enterprise docs with no equivalent surface in this OSS engine — do not attempt to replicate them here:

- **Hub** — multi-environment/cluster admin, its own permission model (`hub:<area>:<type>:<action>`), Elasticsearch-backed reporting. This repo has one engine, one datasource, no cluster-of-clusters concept.
- **Engage** — customer messaging/chatbot channel, WhatsApp/WeChat integration, its own DB tables. Unrelated to BPM/CMMN/DMN execution.
- **Inspect** — enterprise debugging/test harness for Work/Engage releases.
- **Aggregate reporting/analytics dashboards** — none of this repo's REST modules expose a dedicated reporting/aggregation resource (no `Report*Resource` or count-by-dimension endpoint was found across `flowable-rest`, `-cmmn-rest`, `-dmn-rest`). Any dashboard tiles Control shows (e.g. counts of running instances, open jobs) must be built from the existing paged query resources' `size`/`total` metadata, not from a purpose-built analytics API — keep expectations for this modest until/unless new backend aggregation endpoints are scoped separately.

## 10. Proposed Module Layout

Each UI ships as its own module directly under `modules/`, alongside this repo's existing `flowable-*` engine modules but named `togetherflow-*` rather than `flowable-ui-*` — carrying the product's own brand (§1) rather than the engine's, the same way an application built on a database doesn't take the database's name. Wired into the build via `frontend-maven-plugin` (installs a pinned Node/npm, runs the JS build during `mvn package`) so `./mvnw install -Pdistro` can still produce a single deployable artifact per app, per this repo's Maven reactor convention ([CLAUDE.md](../../CLAUDE.md) §Architecture):

```
modules/
  togetherflow-common/       # shared: typed API clients, design system/component library,
                             # auth context, i18n scaffolding, table/diagram-viewer primitives
  togetherflow-shell/        # login + app switcher + routing shell
  togetherflow-work/         # §7.1
  togetherflow-control/      # §7.2
  togetherflow-identity/     # §7.3
  togetherflow-design/       # §7.4 — model library, BPMN/CMMN/DMN/Form/Event modelers, app builder
  togetherflow-attachment-gateway/  # §7.6 — OPTIONAL small Spring Boot backend, only deployed when
                                    # the sharepoint or filesystem attachment provider is configured
  togetherflow-event-recorder/      # §7.2 — OPTIONAL inbound event log (ADR 0015). A library, not a
                                    # service: registry dispatch is in-JVM, so it runs inside the app
                                    # hosting the event registry engine. Off unless enabled.
```

Each module: `pom.xml` (frontend-maven-plugin, produces a static `dist/` and optionally a thin Spring Boot static-hosting jar mirroring `flowable-app-rest`'s packaging style) + standard Vite/React/TypeScript project layout under `src/main/frontend`. `togetherflow-common` is a plain npm workspace package the others depend on, not a deployable. `togetherflow-attachment-gateway` is the one exception to this shape — it's a plain Spring Boot Java module (REST-in, REST-out proxy), not a frontend build, following the same pattern as `flowable-app-rest`.

Suggested stack for `togetherflow-common` (open to revision): React 18 + TypeScript, Vite, TanStack Query for server state (matches the paged/query-heavy REST resources well), TanStack Table for the dense grids Control needs, a component library (or a decision to build a minimal in-house one — flag as an open question, §11). Control uses read-only `bpmn-js`/`dmn-js` viewers for diagram rendering; `togetherflow-design` alone additionally pulls in their full Modeler-mode editors plus a from-scratch CMMN canvas (§7.4.3) and form builder (§7.4.6) — the design-time libraries stay scoped to that one module rather than bloating `togetherflow-common`.

## 11. Open Questions

1. ~~**Component library**~~ — **Resolved.** A minimal in-house design system, built in `togetherflow-common`. See [ADR 0001](adr/0001-in-house-design-system.md).
2. ~~**Deployment shape**~~ — **Resolved.** Each app is a static SPA packaged inside a Maven jar, with a per-app container image. See [ADR 0002](adr/0002-spa-packaged-as-jar.md).
3. ~~**Auth target**~~ — **Resolved.** OIDC Authorization Code + PKCE is implemented against a `togetherflow-ui` public client added to the checked-in Keycloak realm; Basic is fenced to local development. See [ADR 0006](adr/0006-oidc-authentication.md).
4. ~~**Form rendering**~~ — **Resolved.** A Flowable-schema-native renderer, shipped in Phase 2 for task forms and start forms, with the variable grid retained as a fallback. See [ADR 0007](adr/0007-flowable-native-form-renderer.md).
5. **Priority order** across Work / Control / Identity — confirm Work-first matches actual usage priority before Phase 1 kicks off.
6. ~~**CMMN canvas strategy**~~ — **Resolved.** A custom graphical canvas was chosen and built (hand-written SVG); `cmmn-js` was evaluated and rejected as six years unmaintained and incompatible with the diagram-js generation already in use. See [ADR 0009](adr/0009-cmmn-canvas.md).
7. ~~**Form/Event draft-model repository**~~ — **Resolved.** Authoring is client-side; drafts live in the existing generic model repository (`/repository/models`, categories `togetherflow:form` and `togetherflow:event`), so no backend module was needed. Probing a running engine settled it: there is no form REST module and the stock image does not initialise a form engine, while the event registry REST surface is mounted and accepts one `.event`/`.channel` per call. Forms therefore deploy inside an app; events deploy directly. See [ADR 0010](adr/0010-form-and-event-authoring.md).
8. **Model library scope** (§7.4.1): is a single unified "Design" library across all model types the right IA, or should each model type get its own top-level nav item (closer to the legacy Modeler app's tabbed layout)?
9. ~~**Tenant model**~~ — **Resolved in practice.** A switcher was built and tenant context threads through every query from Phase 1, so the more expensive of the two options is the one in place and nothing needs retrofitting. See [ADR 0004](adr/0004-tenant-context-from-day-one.md). Still worth ratifying that a multi-tenant switcher is wanted at all, since a fixed-per-login deployment could hide it.
10. ~~**"Local" attachment storage — DB or filesystem?**~~ — **Resolved in practice.** `db` remains the default and needs no gateway. The `filesystem` provider is now built and verified end to end in `togetherflow-attachment-gateway`, so either meaning of "local" is available; choosing it is deployment configuration, not a code change.
11. ~~**SharePoint auth model**~~ (§7.6) — **Ratified: app-only.** Client credentials, one service identity for every upload. The consequence is stated rather than buried: SharePoint sees the gateway, not the end user, so every file carries the service identity as its author and SharePoint's own audit log attributes every upload to it. A requirement of the form "SharePoint must record which *person* uploaded this" is **not** met by this and needs delegated auth, which would add a second identity provider in the shell, token exchange in the gateway and per-user consent — it is not built. TogetherFlow's own audit trail is unaffected: the engine records the attachment against the task with the real user on it. The provider remains the one integration in this repo **not** verified against the real service, but it is now covered by a contract-level suite against a stubbed Graph — which found and fixed a real defect in the upload URL. See the gateway README.
12. ~~**SharePoint target scope**~~ — **Resolved: one site/library per deployment, configured per gateway.** `togetherflow.attachments.sharepoint.{site-id,drive-id,folder-path}` are gateway-wide, and a deployment that needs a library per tenant runs a gateway per tenant rather than making the store tenant-aware. That keeps the credential boundary and the storage boundary the same thing: a per-tenant library implies per-tenant app registrations and secrets, and a single gateway holding all of them is a much larger blast radius than a config schema change. Revisit only if Open Question 9 settles on tenants sharing one deployment *and* one identity.
13. ~~**Inbound event log**~~ — **Resolved and built.** Option (c): an optional module, `togetherflow-event-recorder`, rather than a change to the engine's versioned schema. It records what arrives on a channel and serves the `GET` the engine never had; Control shows it as a **Received** tab that appears only where the recorder is deployed. Note the seam changed during implementation: `EventRegistryEventConsumer` — the obvious hook, and the one this question originally proposed — cannot serve it, because `EventInstance` carries no channel reference. The recorder sits on `InboundEventProcessor` instead, which also sees the two outcomes a consumer never does: a payload that resolved to no event, and one the pipeline rejected. See [ADR 0015](adr/0015-inbound-event-log.md).

## 12. Suggested Phasing

Phasing sequences *build order* only — every item below is an already-scoped requirement (§7), not a maybe.

- **Phase 1** — `togetherflow-common` foundations (API client codegen, auth, shell) + `togetherflow-work` MVP (task inbox, task detail/complete, start process/case).
- **Phase 2** — `togetherflow-identity` (small surface, unblocks privilege-gated access to later apps) + real form rendering in Work once a decision lands on Open Question 4/7. Attachment storage needs nothing extra here — Phase 1's Work MVP already gets the `db` provider for free (§7.6); `togetherflow-attachment-gateway` (SharePoint or filesystem) only gets built if/when Open Questions 10–12 are answered and a non-default provider is actually needed.
- **Phase 3** — `togetherflow-control` core (process/case instances, jobs incl. external worker, batches, deployments, table explorer).
- **Phase 4** — `togetherflow-design`: model library (§7.4.1) + BPMN process modeler (§7.4.2) + DMN decision modeler (§7.4.4), since both have mature OSS canvas libraries and this repo already has converters/validators for both.
- **Phase 5** — CMMN case modeler (§7.4.3), scoped per whichever answer Open Question 6 gets; app definition builder (§7.4.5) once process/case/decision modeling all exist to compose from.
- **Phase 6** — Form builder + Event Registry channel/event modeler (§7.4.6) — **built**; the draft-repository decision (Open Question 7) is resolved in [ADR 0010](adr/0010-form-and-event-authoring.md). Their Control-side views (§7.2) are built too: deployed channel and event definitions with their live source, and a send-an-event tool. A feed of *received* events was never outstanding frontend work — no engine record and no `GET` resource existed to build it against — and is now served by the optional `togetherflow-event-recorder` ([ADR 0015](adr/0015-inbound-event-log.md)).

Full phase-by-phase detail, dependencies, and exit criteria live in [IMPLEMENTATION_PLAN.md](./IMPLEMENTATION_PLAN.md), including a Phase 7 covering §13 below.

## 13. Production Readiness Requirements

**Answering directly: Phases 1–6 (§12) deliver feature parity with Flowable's own Work/Control/Identity/Design apps — they do not, by themselves, make this production-grade software.** Everything above was scoped against functional requirements only. Production-grade adds a second dimension — security hardening, operability, resilience, verified (not just stated) quality bars, and compliance — that has to be designed in from Phase 1, not appended at the end. This section is that second dimension, made explicit as real requirements rather than left implicit.

### 13.1 Security

- **AuthN**: production deployments use OIDC, not HTTP Basic (§11.3). This repo already has the pieces — `flowable-spring-security` and a working Keycloak realm config (`docker/config/keycloak-flowable.json`) — extend that integration to the new UI modules rather than inventing a second auth mechanism.
- **AuthZ defense in depth**: the UI hides actions a user isn't privileged for (§7.5, §7.3), but every one of those actions must also be rejected server-side by the underlying REST resource regardless of what the UI sends — never rely on UI-side hiding as the actual security boundary. Verify this explicitly per privileged action (start Control's job-retry, deploy in Design, user CRUD in Identity) rather than assuming it.
- **Session handling**: tokens/session state stored in a way that resists XSS exfiltration (httpOnly cookies over `localStorage` for anything sensitive); CSRF protection on state-changing requests if cookie-based sessions are used.
- **Transport & headers**: TLS everywhere in production (terminated at the load balancer per the existing `docker/config/loadbalancer-rest-postgres.yml` pattern, or in-app); a Content-Security-Policy tight enough to block inline-script injection, particularly important for Design's rendered BPMN/CMMN/DMN XML and Work's rendered forms, both of which display content that ultimately came from a deployed model.
- **Supply chain**: dependency vulnerability scanning (npm audit / Dependabot / Snyk-equivalent) wired into CI for every `togetherflow-*` module; container images signed the same way this repo already signs its other images (`docker/cosign.pub` — extend that practice to UI images, don't introduce an unsigned exception).
- **Secrets**: SharePoint client credentials (§7.6), OIDC client secrets, DB credentials — never in source, sourced from whatever secrets mechanism the target deployment already uses (k8s Secrets per `k8s/resources/`, vault, etc.).
- **Security review before GA**: run this repo's own `/security-review` process (or equivalent) against each app before its phase is considered done, not as a one-time end-of-project audit — findings from Phase 1's review should inform Phase 2's build, and so on.

### 13.2 Observability

- **Frontend error tracking** — *built, see [ADR 0014](adr/0014-resilience-and-error-reporting.md)*: unhandled exceptions and API failures captured with enough context (route, user role, request id) to debug without asking the user to reproduce it — not just a browser console log.
- **Correlation with backend**: propagate a request/correlation id from each UI action through to the REST call so a Control-observed failure and a browser-observed failure can be tied to the same trace.
- **Health/readiness probes**: each deployable UI module (or its serving container) exposes what a k8s liveness/readiness probe needs, consistent with how `flowable-rest` is already probed in `k8s/resources/flowable-rest.yaml` — new manifests for the UI apps should follow that existing shape, not invent a new one.
- **Structured logging** from `togetherflow-attachment-gateway` (the one module with real server-side logic) — request/response logging with secrets redacted, not raw dumps.

### 13.3 CI/CD & Release Engineering

- Extend this repo's existing, already-mature CI pattern (`.github/workflows/main.yml`, `docker-release.yml`, `docker-release-with-latest.yml`, `helm-release.yml`) to the new modules rather than building a parallel pipeline: per-module lint/typecheck/unit-test/build on every PR, e2e suite (§8) gating merge to main, container image build+sign+push following `docker/build-and-push-all-images.sh`'s existing pattern, and Helm chart entries alongside the existing `helm-release.yml` flow if these ship into the same Helm chart family as `flowable-rest`.
- **Versioning**: each `togetherflow-*` module version tracks (or explicitly decouples from, if that's the choice — but choose deliberately) this repo's own `8.1.0-SNAPSHOT`-style versioning, so operators know which UI version is compatible with which engine version. Document the compatibility matrix once versioning starts, don't leave it implicit.
- **Environments & rollout**: a staging environment that mirrors production configuration (including whichever attachment provider and auth mode production uses) is exercised before any production deploy; a documented rollback path for each deployable artifact.

### 13.4 Resilience

- **Network resilience** — *built, see [ADR 0014](adr/0014-resilience-and-error-reporting.md)*: retry-with-backoff on transient API failures (not on failed business operations — don't retry a rejected task-completion), request timeouts surfaced to the user rather than an indefinite spinner, and graceful degradation when the attachment gateway (§7.6) or an individual engine's REST module is unavailable — the rest of the app should stay usable (e.g. Work should still show tasks even if the attachment subsystem is down).
- **Statelessness**: every deployable UI module (including `togetherflow-attachment-gateway`) must be safely horizontally scalable behind the existing load-balancer pattern (`docker/rest-loadbalancer-postgres.sh` / `docker/config/loadbalancer-rest-postgres.yml`) — no in-memory session state that breaks under multiple replicas.

### 13.5 Performance & Scale — Verified, Not Just Designed

§8 already states performance NFRs (server-side paging, no unbounded client loads). Production-grade means those are *tested*, not just designed for:
- Bundle-size budgets enforced in CI (regressions fail the build, not just get noticed later).
- Load testing Control's list/table views and Design's model save/deploy path against realistically large datasets (the kind of instance/history volume this repo's own DB-scale tests already exercise for the engine — reuse that scale expectation for the UI layer).
- Core Web Vitals tracked for Work in particular, since it's the daily-use, non-technical-user-facing app.

### 13.6 Accessibility — Verified, Not Just Stated

§8 states a WCAG 2.1 AA target. Production-grade adds the verification loop: automated accessibility linting (axe-core or equivalent) in CI catching regressions per PR, plus a periodic manual audit (screen reader pass, keyboard-only navigation) before each major release — a stated target with no enforcement mechanism isn't a requirement, it's a hope.

### 13.7 Compliance & Data Protection

- **PII awareness**: task variables, attachments, and Identity's user records can contain personal data. Production deployments need a documented data-retention/deletion story (this engine already has history-cleanup jobs, surfaced via `HistoryJobCollectionResource` in Control §7.2 — the UI should make retention policy visible/configurable, not just executable).
- **Audit trail**: `HistoricTaskLogCollectionResource` (already required in §7.1) gives task-level audit history for free — surface it clearly in Work/Control since it's frequently a compliance requirement (who did what, when), not just a debugging aid.
- **Data subject requests**: if this deployment is subject to GDPR/CCPA-style obligations, Identity's user CRUD (§7.3) needs an export/erasure path — flag this to whoever owns compliance sign-off before GA, since "delete a user" and "erase a data subject's personal data" are not automatically the same operation once task history/variables are involved.

### 13.8 Documentation

- **Operator/runbook docs**: how to configure each attachment provider (§7.6), how to point at OIDC vs Basic Auth, how to read the health/readiness signals from §13.2 — written for whoever operates this in production, not just whoever built it.
- **ADRs for the Open Questions** (§11): once each is decided, record the decision and its reasoning (a short Architecture Decision Record per question) so a later engineer doesn't have to reconstruct *why* CMMN got a custom canvas, or *why* SharePoint auth is app-only, from git archaeology.

## 14. UI/UX Quality & Completion Standard

§13 covers whether the system is safe/reliable/operable in production. This section covers a different question: does each screen actually feel finished and professional to use? A feature can be functionally complete (§7) and infrastructurally hardened (§13) while still feeling like a prototype — missing empty states, no keyboard support, inconsistent spacing, silent failures. That gap is closed here, as a concrete per-screen bar rather than a general aspiration to "polish."

### 14.1 Per-screen Definition of Done

Every screen delivered in any phase (§12/IMPLEMENTATION_PLAN.md) must handle **all** of the following states before it counts as done — not just the happy path:

- **Loading**: skeleton/placeholder matching the eventual layout, not a bare spinner, for anything slower than ~200ms.
- **Empty**: a real empty state with guidance on what to do next (e.g. Work's inbox with zero tasks explains that, rather than showing a blank table) — not just "no data" in the middle of an otherwise-populated-looking grid.
- **Zero search/filter results**: distinct from the general empty state — tells the user their filter matched nothing and offers to clear it.
- **Error**: a specific, actionable message plus a retry action wired to the actual failed request — not a generic toast that loses the user's place.
- **Permission-denied**: when a user lacks the privilege for an action or view (§7.3), the UI says so clearly rather than showing a broken/empty screen that looks like a bug.
- **Populated, including pagination edges**: first page, last page, single result, and the server-side paging (§8) boundary conditions — no off-by-one gaps or duplicate rows at page boundaries.

### 14.2 Design system maturity

- A real, documented shared component library in `togetherflow-common` (Storybook or equivalent), not just a grab-bag of one-off components copied between apps — every component documents its own default/hover/focus/active/disabled/loading/error visual states. **Built** as a small in-house gallery (`npm run gallery` in `togetherflow-common`) rather than Storybook, on the same reasoning as [ADR 0001](adr/0001-in-house-design-system.md); coverage is enforced against the filesystem, so a new shared component fails the build until it is documented. `hover`/`active`/`focus` are marked interactive rather than faked — they are CSS pseudo-classes, and rendering them statically would mean duplicating the stylesheet onto gallery-only classes that then drift.
- Design tokens (spacing scale, typography scale, color system, elevation) defined once and consumed everywhere, so Work/Control/Identity/Design read as one product family rather than four separately-styled apps — directly relevant to Open Question 1 (§11.1)'s component-library decision.
- **Color system seeded from the actual brand logo** (`logo.png`, §7.5), not invented independently of it — extracted from the source file:

  | Token | Approx. hex | Logo element | Natural semantic role |
  |---|---|---|---|
  | `brand-navy` | `#0C2347` | "Together" wordmark, person silhouettes | primary text / dark UI chrome |
  | `brand-teal` | `#2AA8AE`–`#3099B7` (gradient) | "Flow" wordmark, cloud outline | secondary brand accent, links |
  | `brand-blue` | `#4898E0` | task nodes in the workflow glyph | primary interactive color (buttons, focus rings) |
  | `semantic-success` | `#8FCB7A` | start-event circle | success states, completed items |
  | `semantic-warning` | `#F5D75E` | gateway diamond | warning states, pending/decision points |
  | `semantic-danger` | `#EE6F6F` | end-event circle | error states, destructive actions (§14.3) |

  The logo's own iconography already encodes a semantic mapping (green=start, gold=decision, red=end) that lines up naturally with success/warning/danger UI states — reuse that mapping rather than picking an unrelated status-color set, so the icon and the UI read as the same visual language. These hex values were extracted from the flat PNG by color quantization, not sourced from a brand guideline — treat them as a faithful starting point, not final: confirm exact values (and get accessible-contrast-checked light/dark variants of each) against a proper brand source once one exists, per the vector-asset gap noted in §7.5.
- Iconography, empty-state illustrations, and loading patterns reused consistently rather than invented per screen.

### 14.3 Interaction & content quality

- **Inline validation**: form fields (task forms §7.4.6, model properties panels §7.4.2–7.4.4, Identity's user/group forms) validate as the user types/tabs, not only on submit.
- **Destructive-action confirmation**: every delete/suspend/deploy-over-existing action (deployments, users, groups, process/case instances) gets an explicit confirmation naming what's about to happen — never a bare "Are you sure?".
- **Autosave / crash resistance for authoring tools**: Design's BPMN/CMMN/DMN/Form editors (§7.4) must not lose work to a browser crash or accidental navigation — periodic autosave to the draft model repository (§5's `ModelResource` note) or an explicit unsaved-changes guard on navigation, at minimum.
- **Undo/redo** within a single modeling session for the canvas editors (§7.4.2–7.4.4) — `bpmn-js`/`dmn-js` both support this natively; wire it up rather than leaving it unused.
- **Consistent feedback system**: one toast/banner mechanism reused everywhere for success/warning/error, and one confirmation-dialog component — not different ad hoc patterns per app.
- **UX writing consistency**: a short content style guide (tone, terminology — e.g. "case" vs "instance" used consistently with this engine's own vocabulary) applied across all error messages, empty states, and confirmations, so copy doesn't read like it was written by four different teams.

### 14.4 Power-user usability

Business users in Work and admins in Control triage high volumes daily — this is exactly the population the legacy apps under-served and where "feels professional" is judged hardest:

- **Keyboard support**: full keyboard navigation (not just tab order — actual shortcuts for claim/complete/next-task in Work, and for common Control actions) plus visible focus states throughout.
- **Bulk actions**: multi-select + bulk operations where the REST layer supports the underlying single-item action at scale (bulk job retry in Control, for instance) rather than forcing one-at-a-time clicking.
- **Saved filters/views**: the legacy Task app supported saved task filters — Work (§7.1) and Control (§7.2) should too, rather than making users rebuild the same filter every session.
- **Fast search**: type-ahead/instant filtering on list views, not a submit-and-wait search form, wherever the backing query resource supports it.

### 14.5 Visual regression & usability verification

- **Visual regression testing**: automated screenshot diffing (Playwright's built-in screenshot comparison, or an equivalent) on the component library and on each app's key screens, so visual polish achieved in one phase doesn't silently erode in a later one — this is distinct from and complements the functional e2e suite in §8.
- **Usability testing loop, per phase, not just at the end**: before a phase in §12/IMPLEMENTATION_PLAN.md is called done, its target persona (§6) — business user for Work, admin for Control/Identity, citizen developer for Design — should actually use it and surface friction, not just have the team review it internally. Feed findings back into that phase before moving to the next, the same way §13.1's security review is scoped per-phase rather than as a single end-of-project pass.

### 14.6 Responsive & cross-device completeness

§8 states Work must work at tablet width. Production-grade means that's verified at real breakpoints (not just "it doesn't break"), touch targets are sized appropriately (not desktop-density controls squeezed onto touch), and the responsive behavior is part of the visual regression suite (§14.5) — covering multiple viewport sizes, not just desktop.
